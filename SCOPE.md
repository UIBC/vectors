# Scope — what a PASS establishes, and what it does not

Generated by `tools/check_scope.py` from `scope/scope.json` and `scope/peers.json`; `python tools/check_scope.py --check` re-renders it and fails on any byte difference. Reviewed 2026-11-25 against uibc-core 0.5.0.

This file says what a PASS establishes and what it does not. Every 'does not' is either demonstrated by a fixture pair that both verify, or already declared by the verifier itself; nothing here is an opinion about our own product.

## 1. What it does establish

| id | a PASS establishes | checks | how |
|---|---|---|---|
| G1 | The package bytes are the bytes the signer signed, under a key the reader can pin out of band. | S6 | Ed25519 seal over identity + manifest + lifecycle; open mode reads the key out of the package, --pubkey pins it. |
| G2 | Evidence entries have not changed since the package was sealed. | S4 S5 | Per-entry SHA-256 plus a Merkle root recomputed from the shipped files. |
| G3 | The declared file set is the file set: no undeclared file sits beside it. | S1 | Package layout check; notes are listed, --strict turns notes into failures. |
| G4 | Identity fields agree with each other and with the lifecycle, and every event actor is an authorised principal. | S2 S3 | Cross-field identity consistency, state machine, actor authorisation. |
| G5 | The checkpoint matches the contents, so truncation is caught; rollback is caught only against a head observed outside the package. | S8 S9 | S8 recomputes the checkpoint; S9 compares it to --expect-head or a state file. |
| G6 | When an RFC 3161 token is shipped, it verifies offline against the CA bundle shipped beside it. | S16 S17 | Signature, message imprint and certificate chain checked without a network. |
| G7 | Six closure components were declared, each with a digest. | S10 | Declaration check only - see N3 for what that does not mean. |

## 2. What it does not establish

Each row is falsifiable: a `fixture-pair` row is demonstrated by two packages that differ only in the property we say is not judged, and both verify; a `verifier-declared` row quotes the verifier's own report. If either stops being true, `tools/check_scope.py` fails.

**N1. It does not establish that the signer is the legal entity named in the package.**

Verification binds a package to a key. The key is a test seed anyone can re-use; nothing in the format links a key to a registry, a domain, or a person.

Evidence: fixture pair `scope/identity/a` + `scope/identity/b` (differs by the owner field: 'alice' against 'acme-medical-devices-gmbh', same signing key) — both PASS.

**N2. It does not establish that the evidence set is complete.**

It can prove an entry was not altered after sealing. It cannot say whether an entry was never taken, because there is nothing to compare the set against. The nine-word version: absence is not evidence of absence.

Evidence: fixture pair `scope/completeness/two` + `scope/completeness/three` (differs by two evidence entries against three, both sealed after the fact) — both PASS.

**N3. It does not compare the files shipped beside a closure digest against that digest.**

S10 checks that six components were declared with digests. The digests are written once, over whatever was on disk at seal time, and files under closure/ sit outside the evidence root, so nothing re-reads them. Replace a closure file after sealing and the declared digest points at bytes that are no longer there - the package still verifies. Nor is the content judged: a one-line file named model_weights.txt satisfies the declaration either way.

Evidence: fixture pair `scope/closure/placeholder` + `scope/closure/wrong-digest` (differs by the closure file body after sealing - one still hashes to the declared digest, one does not) — both PASS; S10 detail says 'declaration only, contents are not verified'.

**N4. It does not establish when the package existed unless an external token is present.**

A timestamp inside the package is written by whoever built it. Only an RFC 3161 or OTS anchor, checked against a source the reader trusts, moves the claim from 'the author says' to 'a third party says'.

Evidence: the verifier says so itself: "Timestamps are not independently anchored.".

**N5. It does not evaluate the agent's behaviour.**

The verifier answers whether a record is intact and internally consistent. Whether the recorded action was correct, safe, or compliant is a different question, judged by a different instrument.

Evidence: the verifier says so itself: "behavioral evaluation".

**N6. It does not verify the signatures on lifecycle events.**

Event signatures are not ratified in the format and the verifier does not check them; a lifecycle chain is checked for order and actors, not for per-event attestation.

Evidence: the verifier says so itself: "lifecycle event signatures".

## 3. Where it fits

| industry | fit | why | covered by someone else |
|---|---|---|---|
| Medical device QMS and cybersecurity file | `strong` | The reviewer wants records that survive ten years, verify without a vendor online, and show exactly what was and was not covered. That is the shape of this format, and the FDA/MDR documents ask for retained, reproducible evidence rather than a live service. | — |
| Audit, legal and settlement records | `strong` | Low volume, high value, adversarial later reading: the reader needs to attack the record, not trust a dashboard. | — |
| Supply-chain handoff between parties | `workable` | An offline package plus an external time anchor covers the handoff; the weak part is entity identity (N1), which the parties have to solve contractually. | — |
| Consumer content provenance (images, video, audio) | `out` | Out of scope by design: this format carries no asset-to-manifest hard binding, no soft binding, and no ingestion at capture time. | C2PA |
| High-volume agent telemetry | `out` | Cost structure: per-record sealing, a Merkle tree, a receipt chain and an anchor is priced for records someone will litigate over, not for a million rows a day. | sigstore (Rekor) signs at volume; no anchoring scheme is priced per million rows |
| Regulatory certification or accreditation | `out` | No accreditation, no notified body, no scheme ownership. Saying a product 'complies with MDR' or 'satisfies FDA guidance' on the strength of a passing verifier would be an overclaim, and this repository does not make it. | notified bodies under Regulation (EU) 2017/745 Annex II and FDA premarket review - assessment activities, not formats |

## 5. The rule this file follows

A limitation that nobody can re-check is a marketing line. So: no limit may be asserted unless it is demonstrated by a fixture in this repository or quoted from the verifier's own report, and no guarantee may cite a check the verifier does not emit. Both are enforced by `tools/check_scope.py`, which is also a gate in `tools/stranger.py` and a job in CI.
